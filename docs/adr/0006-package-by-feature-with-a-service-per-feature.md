# Package by feature, with a service per feature

One `app` package holding every feature's HTTP handlers, SQL and LLM prompts stopped being navigable as features grew, so code is grouped by feature (`internal/recipes`, `internal/profile`, later `internal/planning`, …), each split into the same tiers: handlers (HTTP and form parsing) call a `Service` (use cases in domain types, validation, transaction boundaries), which calls unexported store functions (SQL taking a `db.Querier`, so a caller's transaction can span several stores). Every feature has a `Service`, even a thin one, so each feature looks the same; the feature also owns its templ views and its LLM jobs. Each file holds one tier, named by its prefix: `web_` (handlers, form parsing, templ views, Messages), `service` (the `Service`, its use cases and LLM jobs) or `store` (SQL and other external stores), and `internal/web/tiers_test.go` checks it. Shared machinery sits beside the features and never imports them: `domain` (pure rules), `agent` (the LLM loop), `runs` (the Run engine, Traces and their pages), `db`, `httpx`, `web` (layout, shared components, assets), `clock`, `telemetry` and `apptest`. `runs` has a feature's three tiers, so its files keep to them too. `app` only wires these together and keeps the one route table, so every URL and its middleware is listed in one place.

## Considered Options

- **Layered packages** (`postgres`, `http`, `jobs` across all features), as in hexagonal architecture: no import cycles possible, but every feature is spread over several packages that all grow with each feature.
- **Keep one `app` package**, split into files by concern: cheapest, but nothing enforces the boundaries.
- **Handlers calling stores directly**, no service: less code today, but transaction rules ended up in handlers, and planning will need use cases that span features.

## Consequences

- Every table has one owning feature, and the owner's code holds the table's rules. Ownership follows the rows' lifecycle, which feature creates and deletes them and in whose transaction, not the noun: a planner's Recipe Draft is made and dropped with its Plan Proposal, so `planning` owns `proposal_recipe_draft`, not `recipes`.
- Features may import `runs` and other features' services, but dependencies must stay one-way: if two features need each other, the shared part moves into `domain` or a new package. A feature may write the tables of a feature below it in that graph, never those of one above it.
- A write down the graph: a feature may export a write taking a `db.Querier` for the features depending on it, so their transaction spans it. It lives in a `service` file and holds every rule its owner enforces for that write, since the owner's `Service` doesn't run: `recipes` adds a Recipe's new Ingredients through `ingredients.AddIn`, and `planning` accepts its Recipe Drafts through `recipes.AcceptDrafted`.
- A write up the graph, into a feature that depends on the caller, is never allowed. A feature that only needs to read what a feature depending on it owns takes a function for it, which `app` wires: `ingredients` asks whether a Recipe or a Plan Proposal uses an Ingredient through `recipes.RecipesUsing` and `planning.UsesIngredient`. Only for reads: a write in the caller's transaction moves the shared part below both, as `ledger` did (ADR-0019).
- A feature whose rows another feature's store functions read exports its loaders in its `store` file, taking a `db.Querier` so the caller's transaction spans them, rather than the reader querying its tables: `kitchen`, `recipes` and `planning` load Ingredients through `ingredients.LoadIngredients`, and `planning` loads Portions through `ledger.LoadPortions`. An exported store function is a read: its SQL never says `INSERT`, `UPDATE`, `DELETE` or `FOR UPDATE`, which `internal/web/tiers_test.go` checks. Every function `app` wires into a `Service` is one, so this also keeps them reads.
- A foreign key into another feature's table is a rule that feature must know about: its deletes check for the referring rows through a read, never cascade into them. Deleting an Ingredient asks `ledger.HasMovements`, `recipes.RecipesUsing` and `planning.UsesIngredient` first.
- `runs` sits below the features, so its API sharing a transaction with the caller is a write down the graph: `Engine.CancelIn` cancels a Run in it, `Engine.Start` runs the caller's link to the new Run in the transaction recording it, and `Engine.Leaves` stores what a Run leaves in the one recording its success.
- Stores are concrete and not behind interfaces; tests hit a real Postgres through `apptest`. Interfaces are kept for external, non-deterministic dependencies (`agent.LLM`, the Playwright MCP client).
